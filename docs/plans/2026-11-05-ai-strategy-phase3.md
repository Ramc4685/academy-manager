# AI strategy, Phase 3 build plan

Written 2026-11-05, while Phase 2 was still merging (A1, A2, A4, B1, B2 on `main`; A3, B3, B4, B5, B6 open and green). Parent plan: `2026-11-04-ai-strategy.md`, section 4 "Phase 3, later", sections 5, 7 and 9. Sibling: `2026-11-04-ai-strategy-phase2.md`. Phase 3 is the quarter after Phase 2 ships: lead nurture on real channels, a constrained question-answering surface over existing reports, the technique video pilot if the evidence allows it, and copy generation.

Nothing in this document is built. It is a plan for a build session and a list of decisions for the owner.

## The gates that shape the order

Phase 3 has four owner gates, and three of them are outside the code. The build session cannot start a gated slice on its own; it reaches the gate, asks the exact question listed in "Owner gates" below, and does the ungated work meanwhile.

- **Channel accounts.** SMS needs a registered 10DLC brand and campaign on a Twilio (or equivalent) account the owner owns; WhatsApp needs a Meta Business account, a WhatsApp Cloud API number and approved message templates. Registration takes days to weeks and costs money. The unofficial OpenWA pilot the owner runs for BLNO is never a product channel (strategy section 8).
- **Growth customers.** Phase 2's rule stands: AI features are built for paying academies. Phase 3's paid slices start only when the owner confirms the Growth pre-sale landed (card on file by 2026-12-01) and says how many academies are on Growth. One is enough to build; zero means Phase 3 is nurture automation and copy only.
- **Counsel on video.** The technique video pilot (strategy section 6) needs a per-child AI/video consent and a retention policy reviewed by counsel before the first clip, and the section 7 accuracy test passed. Neither exists yet. The Phase 1 "legal groundwork" item (AI clause and per-child AI/video opt-in in the waiver flow, stored and unused) was left out of the Phase 1 build by the brief, so it is a Phase 3 slice here.
- **Vendor and residency** (strategy decision 3). Still open. The Anthropic adapter on the paid API is what exists; children's clips and voice never go anywhere until the owner confirms the vendor and whether US-only residency is required.

## Slices

Every slice: one agent, one PR, one release note. Every model-calling slice: `has_feature(academy, "ai")` or the free cap decides access, `assert_under_cap` before the call, `record_ai_call` after, prompt versioned in `PROMPTS`, strict parse through `json_answer.py`, the model sees exactly what the slice states, a human approves before anything reaches a parent or a lead. Every slice lists the **shared files** it touches so the Workflow can serialize them. The recurring shared files are `backend/v2/interfaces/admin/router.py`, `backend/v2/main.py`, `backend/v2/composition/ai.py`, `backend/v2/contexts/ai/domain/prompts.py`, `backend/v2/contexts/ai/README.md`, `frontend/lib/query/keys.ts`, `frontend/lib/api/admin.ts` and the Settings notify panel.

### Track C: lead nurture (automation first, then channels)

**C1. Nurture sequence engine, email only, marketing consent required.** A per-academy sequence of up to four steps for leads with `consent.marketing` true and pipeline status `lead` or `trial`: day 0 is the existing acknowledgement, then owner-written templates on days 2, 7 and 21 with merge fields only (academy name, class, seat band, booking link). One daily job per the `trial_follow_ups` shape, idempotent per (contact, step) with a unique index, stopped by any inbound reply, pipeline move, unsubscribe or `enrolled`. Category `CAMPAIGN`, so the CAN-SPAM footer and `ProspectOptOutGate` apply unchanged. Admin UI: a sequence editor on the pipeline settings with a preview and an on/off switch per academy, default off. No model. Free. Shared files: `main.py` (job), `admin/router.py`, `keys.ts`, migration (sequence state and index). Gate: none.

**C2. Channel port and SMS adapter (10DLC).** A `MessagingPort` beside `LlmPort` with one adapter for Twilio over plain `httpx` (the repo's pattern: no SDK, constructed only in composition under `V2_SMS_ENABLED` plus credentials, structural test that fails on any other construction site). Phone consent: a new `ContactConsent.sms` boolean captured on the public form with the TCPA wording, stored with `captured_at`, false by default; STOP/HELP keyword handling through the inbound webhook, suppression keyed on phone digits, quiet hours in the academy's timezone. The adapter delivers only through the send gate and the outbox, logs to the family contact log, and the first use is C1's steps when the lead has `sms` consent and no email. No model. Free, but a per-message cost line appears on the platform tenant view. Shared files: `main.py` (webhook router include), `settings.py`, public `TrialRequestForm.tsx`, migration (consent field, suppression index). Gate: **owner gate 1**, a live Twilio account with an approved 10DLC campaign; the slice is built and tested against the stub before that, but the production credentials are the owner's per-action approval.

**C3. WhatsApp Cloud API adapter.** Second adapter on C2's port: Meta Cloud API, template messages only outside the 24-hour customer-service window, template ids held in tenant settings, inbound webhook with signature check, opt-in recorded as `ContactConsent.whatsapp` from a form tick or an inbound message. Replaces nothing: the `wa.me` links stay for human-pressed sends. No model. Shared files: `main.py`, `settings.py`, `TrialRequestForm.tsx`. Gate: **owner gate 1b**, a Meta Business account, a Cloud API number and approved templates. Depends on C2.

**C4. AI step drafting for the sequence (paid).** In the C1 editor, "Draft this step" calls the model with the academy's public class lines, the step's purpose and the previous steps' text; the owner edits and saves. The model never sees a lead. Prompt `nurture_step`. Shared files: `prompts.py`, `ai/README.md`, `composition/ai.py`, `admin/router.py`, `admin.ts`. Gate: **owner gate 2** (Growth count). Depends on C1.

### Track D: ask the academy

**D1. Hard AI cap.** Replace the count-then-insert check in `RecordAiCall.assert_under_cap` with a reserve on a per-academy per-month counter document (`$inc` with a `$lt` filter), released on provider error, so the cap cannot be passed by concurrent calls. Keep the soft free-cap prompt from A3 as the UI; this is the ceiling under it. Also a per-feature daily ceiling read from the academy document (`ai.daily_call_cap.<feature>`), because a chat surface is the first feature a user can call in a loop. No model. Shared files: `record_ai_call.py`, `mongo_ai_call_repo.py`, `ai/README.md`, migration (counter collection). Gate: none. Every D slice depends on it.

**D2. Tool-schema layer.** `contexts/ai/application/tools.py`: a registry of read-only tools, each a name, a one-paragraph description, a pydantic argument model and a callable that invokes the existing report use case under the caller's tenant scope and persona. The first registered tools are exactly the thirteen report endpoints listed above, wrapping their existing use cases, not the HTTP routes. A tool result is the typed response model serialised and truncated to a stated size. Unit test: every registered tool's argument schema round-trips through the Anthropic tool-use shape, and a tool called with another academy's id returns that academy nothing. No model call in this slice. Shared files: none outside `contexts/ai/` and its README. Gate: none. Depends on D1 only for the cap semantics it will be called under.

**D3. Ask the academy, owner persona (paid).** `POST /admin/ai/ask` with a question; the use case runs a bounded tool-use loop (at most four tool calls, one model turn after the last) with D2's registry as the only tools, system prompt `ask_academy`, and returns the answer plus the list of tool calls made and their arguments, shown to the user as "what I looked at". Every number in the answer must appear in a tool result (B5's test, generalised). Owner-only through `owner_gate.py`; each question is one `ai_calls` row per model turn; D1's daily ceiling applies. Frontend: a drawer on the reports page, not a chat history; nothing is stored but the audit rows. Shared files: `prompts.py`, `ai/README.md`, `composition/ai.py`, `admin/router.py`, `admin.ts`, `keys.ts`, reports page. Gate: **owner gate 2**. Depends on D1 and D2.

### Track E: technique video pilot

**E1. Per-child AI/video consent and retention policy, stored and unused.** A separate per-child opt-in in the waiver flow (`contexts/onboarding`), naming the model vendor, with the retention schedule text, versioned like the platform agreement (version, accepted at, accepted by); a parent can revoke from the parent app; a `consent_ai_video` read path that every later E slice must call. The text ships as a placeholder the owner replaces after counsel. No model, no upload. Shared files: waiver routes, parent and admin waiver UI, migration. Gate: **owner gate 3a**, the owner confirms BLNO is the pilot and will pay counsel; the slice can be built with placeholder text before counsel signs off, but nothing in E2 or E3 starts until the text is the reviewed one.

**E2. Accuracy test harness, offline.** A script under `scripts/dev/` that takes a folder of side-on clips and a coach's CSV of pass/fail per criterion, runs MediaPipe pose on a laptop with the face landmarks dropped before anything is stored, computes joint angles for the Level 1-2 grip and lunge criteria, and prints separation (pass vs fail) per criterion with the "can't tell" rate. Nothing goes to any model or server. This is the section 7 test; its output is the gate for E3. Shared files: none (new script, `requirements-dev`). Gate: **owner gate 3b**, twenty consented clips exist; the clips never enter the repo.

**E3. Clip capture and coach review, one academy (paid add-on).** Only if E2 shows the angles separate pass from fail and counsel has signed E1's text: a coach-app capture of a 10-20 second clip for one student with `consent_ai_video` true, pose on device, only candidate frames and joint angles uploaded, the model proposes up to three criterion-tied observations with "can't tell" allowed (prompt `technique_video`, extending B6's text observation), the coach approves or discards, the parent sees only approved text in the existing wins and report card, raw clip deleted on a schedule (30-90 days, the E1 policy's number) by a job. Feature flag `ai.technique_video_pilot` on exactly one academy. Shared files: `prompts.py`, `ai/README.md`, `composition/ai.py`, `coach/router.py`, `main.py` (deletion job), `coach.ts`, `keys.ts`, migration. Gate: **owner gates 3a, 3b and 4** (vendor confirmed for children's data). Depends on E1, E2, B6.

### Track F: copy generation (paid, cheap, last)

**F1. Campaign copy draft.** In the existing campaign composer, "Draft" from a one-line purpose, the audience name and the academy's public class lines; the owner edits and sends through `SendCampaign` unchanged. Prompt `campaign_copy`. The model never sees recipients. Shared files: `prompts.py`, `ai/README.md`, `composition/ai.py`, `admin/router.py`, `admin.ts`, campaign composer. Gate: owner gate 2.

**F2. Public-page copy draft.** "Draft" for `about_text`, `highlights`, FAQ answers and coach bios from the academy's name, sport, programs and the owner's notes, saved only through the existing public page content card. Prompt `public_page_copy`. Shared files: `prompts.py`, `ai/README.md`, `composition/ai.py`, `admin/router.py`, `admin.ts`, `public-page-content-card.tsx`. Gate: owner gate 2. ## How the build session runs it

Phase 2's lessons shape this: slices that touched `admin/router.py`, `keys.ts`, `prompts.py`, `ai/README.md` and `main.py` conflicted with each other after every merge; the pre-push gate takes about 40 minutes and crashes the private mongod when two run on it at once; agents cannot merge, reply to or resolve review threads under the auto-mode classifier.

- **One worktree per slice off current `origin/main`**, cut only when the slice starts (not all at once; Phase 2 ran out of disk). One Workflow, phases below. Each slice an isolated agent that commits and does not push; a review agent per PR (cheaper model, verifiers first); the orchestrator pushes each branch in a background Bash so the pre-push hook runs the gate (never `--no-verify`), opens the PR with a release note in `docs/release-notes/` carrying the three exact sections and the real PR number, and stamps the number after the PR exists.
- **Phase 1, ungated, parallel:** C1, D1, D2, E1, E2 at once. They share no files: C1 owns `main.py` and `admin/router.py` for this phase, D1 and D2 stay inside `contexts/ai/`, E1 is in onboarding and the waiver UI, E2 is a script.
- **Phase 2, channel lane, serial:** C2 then C3, because both touch `settings.py`, `main.py` and the public form. Both are built and gate-tested against stubs while gates 1 and 1b are open; the PRs say "stub only" in the deploy notes until credentials exist.
- **Phase 3, AI lane, serial on the `prompts.py` lane:** D3, then C4, then F1 and F2 together. Every one of these touches `prompts.py`, `ai/README.md`, `composition/ai.py`, `admin/router.py` and `admin.ts`, so they run one at a time and each is cut from `main` after the previous one merges. This is the single biggest change from Phase 2, where six slices appended to those files in parallel and every merge produced the same six conflicts.
- **Phase 4, video lane:** E3 alone, after gates 3a, 3b and 4.
- **One private mongod per gate run.** The orchestrator starts a mongod on a reserved port per concurrently pushing branch (27993 and 27995 and up), sets `V2_MONGO_URL` for that push only, and never runs two gates on one mongod. Phase 1 above has five pushes; they queue on at most two mongods.
- **Merge-when-green, in the Workflow, after the owner's standing yes for that slice:** a step that polls the PR's checks on its exact head SHA, merges with `gh pr merge --squash` only when `CI Gate` and `Release Notes Gate` are both green on that SHA and the PR is mergeable, and otherwise reports and stops. It never pushes to a slice branch, never rebases, never re-runs a failed check and never merges a PR whose head moved since the check. Conflicts with `main` are resolved by the slice's agent in its worktree (merge `origin/main` in, run the backend subset, commit, gate, push), then the step tries again. The owner can take the step over at any time by merging themself; the step detects the merged state and continues.
- **Stop points.** The session stops and reports after Phase 1 (five PRs open), after each gate question, and after the AI lane. Nothing is deployed by the session; production is the owner's approval on the Production workflow, migrations by hand as today.

## Owner actions and open decisions

- Confirm the Phase 2 end state: A3, B3, B4, B5, B6 merged and deployed, `V2_AI_ENABLED` and `V2_ANTHROPIC_API_KEY` set, Growth price id on `plan_growth`, `ai.coach_review_narratives` given a UI. Phase 3 slices cut from a `main` that has them.

Same for Meta Business and a Cloud API number if WhatsApp is wanted in this phase; otherwise say so and C3 is dropped.

- **Gate 3a** (strategy decision 2): is BLNO the technique pilot, and will the owner pay counsel to review the per-child AI/video consent and retention schedule? Also decide the retention number (30, 60 or 90 days).
- **Gate 4** (strategy decision 3): vendor and tier for children's data, US-only residency yes or no. The Anthropic paid API is the default if nothing changes; the DPA names it.
- **Decision 4 carried forward:** the free-tier cap is 20 soft (A3). D1 adds a hard ceiling; propose 200 a month hard (today's default) and 50 a day per feature for "ask the academy". Confirm or change the numbers.
- **New decision:** may C1's nurture steps go to a lead on the strength of `consent.marketing` alone, or does the owner want a separate "nurture" tick on the form? The code treats `marketing` as the consent today; a separate tick is a one-field change in C1 if wanted.
- **New decision:** sender identity for SMS and WhatsApp. One platform number shared by all academies (cheaper, one 10DLC campaign, messages open with the academy name) or one number per academy (costlier, needs a campaign each, cleaner for parents). Propose one platform number for the first five academies.

Not verified in this plan: Twilio and Meta registration lead times and fees as of today, whether BLNO's lead volume justifies a paid channel at all (ask the owner for inquiries per month before building C2), and whether the thirteen report use cases can run under a tool call without their HTTP dependencies (D2's agent checks each; any that cannot is left out of the first registry).
