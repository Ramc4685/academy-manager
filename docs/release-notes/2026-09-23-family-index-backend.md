# People CRM family index (backend): GET /admin/families and /admin/families/summary, alias-aware Family billing, migration 0193

PR: #925

## What changed

- New read-only admin routes, both `require_persona("admin")`: `GET /api/v2/admin/families` (one row per family record: parent contact, children with their lifecycle chips and classes, the rolled-up family stage, card and registration state, and a `money` block) with `search`, `scope` (`active` / `leaving` / `left`), `stage`, `class_id`, `card_on_file`, `overdue`, `sort` (`name` / `stage` / `balance` / `children`), `order` and pagination, sorted before paginating; and `GET /api/v2/admin/families/summary` (the Active / Leaving / Left tiles over the unfiltered index, counts per stage, and static view presets). No frontend change; the Families view that consumes these ships separately.
- The read model lives in the CRM context (`contexts/crm`): the family stage is the most urgent child state, in the spec §6 order `pending_cancel > active > at_risk > on_hold > paused > trial > never_enrolled > left`; each child's state is the same derivation the Students page shows. Search matches child and parent names (word prefix), email, legacy roster parent fields and phone numbers by their last 7 to 10 digits; a child match names the child so the UI can make it the result row. The whole academy is read in a fixed number of queries (a test pins 3 and 30 families to the same count), cached for 60 seconds per academy. Wiring is the new `composition/families_crm.py`; nothing was added to `composition/admin.py`.
- Parent alias resolution: a child whose parent reference is stored under the roster `user_id`, the `firebase_uid`, an `auth_uid` or the users `_id` now lands in the right family. Identity's new `resolve_parent_aliases` asks one `$in` per field and never an `$or` across fields; the list's staff check (`list_existing_user_ids`) now uses it too.
- The Family billing page (`GET /admin/families/{parent_id}/billing`) is alias-aware: students, invoices, the card row and credit are read under every alias of the parent with one equality lookup per alias and field, replacing the `$or` across `parent_id` and `parent_user_id`. A family whose children or invoices were stored under the Firebase uid now shows them, and the list and the Billing tab show the same balance (both use the new `billing/application/family_money.open_balance`; a test checks they agree for a child stored under `firebase_uid`).
- Money visibility has one seam, `can_view_family_money(claims)` (the #553 staff-tier seam): today owner or admin, which is every caller of these admin routes. When it says no, every `money` block is null, balance sorting falls back to name and the Overdue filter matches nothing. Staff tiers themselves are not built.
- Saved views are static presets returned by the summary (Active, Leaving, Left, Overdue, No card). Persisted per-academy Groups (`family_groups`) remain Phase 4.
- Migration `0193_users_parent_alias_lookup_indexes` adds `users_user_id_lookup` and `users_auth_uid_lookup` (plain, non-unique). `explain()` on a real mongod showed both alias lookups were collection scans; every other lookup the index and the billing page issue is already served. If an equivalent index already exists under another name, the migration leaves it alone.
- #894: the real-mongod planner test now also asserts the batched and academy-wide lookup shapes (the four alias lookups, the family index's reads, the billing page's per-alias reads and the parent-keyed portal reads) are index-served. With CI on Mongo 8.0 (#899), the harness (#907) and the waiver `$or` fix (#908) already merged, this closes #894.
- Structural: the enrollment-status-set scan now covers `contexts/crm`, and a new test pins every `/admin/families*` route to `require_persona("admin")`. `full_name_key` moved to `shared/names.py` (re-exported where it was).

## Deploy notes

- Migration 0193 is applied by the production migrate step (dry run, then the Fly release command) per `docs/runbooks/migrations-rollout.md`; expect `pending_before` to list `0193_users_parent_alias_lookup_indexes` (and `0192_crm_contacts` if that PR ships in the same deploy). It builds two indexes on the small, global `users` collection and is safe before or after the code: without it the new list still works, with two collection scans of `users` per build.
- No feature flag, no environment variable, no backfill. The new routes are unused until the Families view ships.

## Risk / rollback

- Medium-low. The new routes are read-only and admin-only. The main behaviour change is on the existing Family billing page: it now also finds students, invoices, the saved card and credit stored under the parent's other ids, so a family that previously showed an empty or partial page can now show more children and a higher balance (the correct one). It issues more, smaller queries per page view (one per alias and field) instead of one `$or`.
- The list's per-family numbers are cached for up to 60 seconds, so a payment recorded a moment ago may take up to a minute to show in the list (the Billing tab is not cached).
- Rollback: revert the PR. Migration 0193's two indexes can stay (harmless) or be dropped with `db.users.dropIndex("users_user_id_lookup")`, `db.users.dropIndex("users_auth_uid_lookup")` and `db.v2_migrations.deleteOne({version: "0193_users_parent_alias_lookup_indexes"})`.
