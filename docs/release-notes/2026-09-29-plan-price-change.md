# Change a plan price from a future month (Settings overhaul Phase 6 PR 26)

PR: #TBD

## What changed

- **"Change a plan price · Preview first"** card on the owner-only Pricing page (`/admin/pricing`). The owner picks a plan, a new monthly price and an "Apply from" month. The preview lists the classes linked to the plan (effective links only), how many students each one bills (the monthly invoice run's own rule: `active` enrollments with a billing type it invoices; paused ones are not counted), totals per month old and new, and "from the <Month> invoice. Invoices already sent never change." Classes on a custom price at the plan's price are listed as not affected. "Apply from <Month>" records the change.
- **Only future months.** The earliest month is next month, or the month after the latest month that already has charges (a recorded monthly run for the academy; an invoice, invoice key or monthly payment for any linked class; a checked-out registration quote for a linked class; or a class-cancellation credit for a linked class dated in that month). The server re-validates on apply: the current month, a past month or an already charged month is a 422.
- **One pending change per plan**, enforced by a partial unique index (migration 0212) so two concurrent applies cannot both land (409). A scheduled change can be cancelled from the card until its month starts, and only while nothing for that month or later is charged or quoted at the new price for its classes (an open registration quote, a checkout, a monthly run generated early, or a class-cancellation credit for a date in that month or later, which is sized from that month's fee when the month is not invoiced yet): otherwise 409 `Billing.PriceChangeAlreadyCharged`, so a month never ends up with two prices.
- **Links and a pending change stay in step.** Marking a class Custom (or linking it to another plan) takes it out of a pending change, so it keeps its own fee; linking a class to a plan with a pending change at the plan's current price adds it, so its link does not go stale. Moving a class off the plan is refused (409) once it is charged or quoted at the new price.
- **The registration quote's "Starting next month, tuition is $X/month"** uses next month's price, so it matches the next invoice when a change starts next month. The quote stores that month (`next_billing_period_label`), and an open or paid quote that told a parent a month's price blocks a cancel (or a class move) for that month like any other charge.
- **Owner edits cannot race a quote or the scheduler.** A cancel, or a class leaving or joining a pending change, first holds the change (a short lease on the change document, `edit`, and a `revision` bump), then checks for charges, then writes. A registration quote reads the change's fence before and after it stores its snapshot: while a hold is open it waits and retries (409 `Billing.PriceChangeInFlight` if it never clears), and a quote that overlapped an edit is marked `SUPERSEDED` and priced again. The scheduler's flips and "applied" mark are compare-and-set on the revision it read, so a change edited mid-run is left for the next daily run. The link audit records only the moves actually written.
- **Class-cancellation credits carry their month.** A credit for a called-off date now records the class and billing month it was priced for (`session_id`, `billing_period` on `account_credit_ledger`, additive). That is what blocks the cancel or class move above. The credit reads the change fence like a quote does; if an owner edit overlapped its pricing, every credit it sized from the class fee is re-sized to the fee now in force (compare-and-set, only while nothing has drawn on it; otherwise logged as `apply_occurrence_cancellation_credit_resize_refused`).
- **How the new price reaches bills.** Every charge path now reads a class's fee *for a billing month* through one function (`class_fee_cents_for_period`): monthly invoice and "Bill this month" (`resolve_monthly_charge`, which also covers first-month proration), checkout quote, move proration and cancellation credits. For a class in the change's snapshot whose stored fee is still the old price, a month on or after the effective month reads the new price; an earlier month reads the old one. With no change on record (BLNO today) it returns the stored fee exactly as before.
- **Links do not go stale.** Once the month starts, the daily monthly-invoice job (03:00 academy time, before generation) moves each linked class fee and the plan price to the new price together, compare-and-set against the old price (a legacy class's `monthly_price_cents` / `monthly_price` move with `amount_cents`). A class fee the owner edited by hand is left alone (the hand-set fee wins, before and after). Charges do not depend on this step: the answer for a given class and month is the same before and after it.
- **"Scheduled: $X from <Month>"** shows on the plan row, on each affected class under "Where each class's price comes from", and under Monthly fee in the class editor (Sessions > class > Edit), until the change takes effect.
- **Audited** in `billing_audit_log`: `plan_price_change_scheduled`, `plan_price_change_cancelled` (owner) and `plan_price_change_applied` (scheduler, actor `system:plan-price-change`).
- **API:** `GET /api/v2/admin/pricing/price-changes/preview`, `POST /api/v2/admin/pricing/price-changes`, `DELETE /api/v2/admin/pricing/price-changes/{change_id}`: owner only, a plain admin gets 403. `GET /api/v2/admin/pricing/scheduled-class-fees` is readable by any admin (the class editor note).

## Deploy notes

- Migration `0212_plan_price_changes` (new collection `plan_price_changes`, four indexes led by `academy_id`, including `(academy_id, edit.session_ids)` for the quote's fence read, the pending one partial on `pending_plan_id $gt ""`). Idempotent, touches no existing data. Run it before or with the deploy; without it everything works except the database-level guard against two concurrent applies (an application-level check still refuses a second pending change).
- Class-cancellation credits issued before this deploy have no `billing_period` and are not counted by the guards. They were all priced with no plan price change on record, so only one case matters: a credit already issued for a future month (a date called off ahead of time), followed by a change scheduled from that month. Before scheduling a change, check for such credits (`account_credit_ledger`, `source_type: "occurrence_cancellation"`, created before the deploy, for a date in a month not yet invoiced).
- BLNO's bills do not change: no change is on record, so every charge path reads the stored class fee exactly as before (pinned by a real-mongod test on a BLNO-shaped academy). Nothing is written until the owner applies a change.

## Risk / rollback

- Risk: every charge path makes one extra indexed lookup per class read (`plan_price_changes` by academy and class). Empty for BLNO. Cancelling a class date also reads the change fence twice (the same indexed lookup) and waits up to about a second while an owner edit of that class's change is open.
- A direct edit of a plan price in the Plans list while a change is pending is still allowed; the scheduled change then leaves the plan price alone at the effective month (compare-and-set) and those class links show as Custom, as any direct plan price edit does today.
- Rollback: revert this PR. If a change has been applied, the class fees and plan price keep the new value (they are ordinary stored fees). If a change is only scheduled, revert means it never takes effect; cancel it first to keep the audit trail tidy. The collection can stay.
