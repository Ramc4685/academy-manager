# fix-self-cancel-end-of-period

PR: #TBD

## What changed
A parent's self-cancel under the `end_of_period` policy no longer flips the enrollment to `cancelled` on the spot (issue #675, owner decision Option A). The enrollment stays `active` with a `pending_cancellation_at` marker (academy-local month end, the same boundary billing uses), so the child stays on the coach roster, the parent schedule and the seat count for the month the family already paid for. A new durable scheduled action `cancel_at_period_end` (`contexts/enrollment/application/use_cases/scheduled_actions.py`, `pause_request_id` now optional) is processed hourly by the new `process_scheduled_cancellation_actions` job (`contexts/enrollment/application/use_cases/process_scheduled_cancellation_actions.py`, wired in `composition/scheduled_cancellations.py`, registered in `main.py`, `SCHEDULED_JOB_MONITORS` and `ops_digest.JOB_STALE_AFTER`), which performs the real cancel at month end: status CAS, seat release, waitlist `EnrollmentCancelled`, occurrence-roster cleanup, lifecycle row, staff alert. Billing sync, the fee line and a `cancellation_scheduled` timeline row still happen at request time. Admin cancel / withdraw / session cancel retire any pending action. The parent route now returns `status: "pending_cancellation"` plus `pending_cancellation_at`, the preview returns `effective_at`, and roster / student / parent DTOs carry `pending_cancellation_at`; the parent dialog shows "Your child keeps their place through Sep 30; October will not be billed" instead of the raw `end_of_period` token, and the admin RosterPanel and parent children page show an "Ends <date>" chip. Immediate timing is unchanged.

Review follow-ups folded into the same change:
- **The two scheduled-action queues can no longer cross-consume each other.** `ScheduledEnrollmentActionRepository.list_due` takes an `action_type` and `MongoScheduledEnrollmentActionRepository` puts it in the Mongo query; both `ProcessScheduledResumeActions` and `ProcessScheduledCancellationActions` pass their own type and keep a Python-side re-check as defence in depth. Previously the daily resume job would pick up a still-pending `cancel_at_period_end` row, no-op it (the enrollment is not paused) and mark it succeeded — destroying the parent's cancellation for good. Filtering in Mongo also stops one type's backlog crowding the other out of the `limit` window.
- **Monthly invoice generation skips a scheduled cancel's later periods.** `MongoMonthlyBillingGenerator.generate_monthly_payments` now reads `pending_cancellation_at`, buckets it into a `YYYY-MM` label in the academy's own timezone (loaded once per run, UTC fallback) and skips any period after it, recording a `pending_cancellation` `skipped_details` entry. Without it the 03:00 UTC generation cron beat the cancel worker's 05:15 UTC tick and minted — and emailed — an October invoice to a family that had cancelled.
- **A failed month-end cancel now retries and then reaches a human.** A transient exception leaves the row `pending` with an incremented `attempt_count` (`mark_retry_pending`) and the next hourly tick retries it, up to `MAX_ATTEMPTS = 3`; only then is it `failed`. `failed` rows are surfaced: the admin attention reader became `list_stuck_scheduled_actions` (`composition/scheduled_cancellations.py`, `list_by_statuses(["blocked_capacity", "failed"])`) and `dashboard_routes.dashboard_attention` splits it into the existing `scheduled_resume_blocked` item and a new high-severity `scheduled_action_failed` item. `enrollment_missing` stays terminal. The processor's module docstring now describes what the code actually does.
- **Smaller correctness fixes.** The admin `RosterPanel` "Ends <date>" chip takes the session/academy timezone instead of `null`, so it no longer renders the academy-local month-end instant in the viewer's browser zone (a UTC browser read "Ends Oct 1" for a Chicago Sep 30). The request-time staff alert uses a new `cancellation_scheduled` roster-change kind instead of a second `cancelled` alert, so coaches are not told twice — three weeks apart — about a student who is still attending. `MongoEnrollmentWriter.update_status` clears `pending_cancellation_at` when an enrollment reaches `cancelled`/`withdrawn`, so an admin cancel on the 20th no longer leaves a stale "Ends Sep 30" chip beside a CANCELLED chip.

## Deploy notes
- New migration `backend/v2/migrations/0169_scheduled_cancel_at_period_end.py`: re-applies the `scheduled_enrollment_actions` validator (0133's definition corrected in place: `pause_request_id` optional/nullable, `action_type` enum widened) and rebuilds 0113's `unique_pause_action` index as a partial index plus a new partial unique `unique_pending_cancel_at_period_end`. It does NOT run on boot (`V2_RUN_MIGRATIONS_ON_BOOT` is false, #629) — apply by hand right after the deploy via `fly ssh console -a courtmastr-academy-api` and `backend.v2.migrations.run_pending_migrations`, same as 0165-0167. Until it is applied, an end-of-period self-cancel returns an error (validation on the first write; nothing is half-written); immediate-timing cancels are unaffected.
- New scheduler job `process_scheduled_cancellation_actions` (cron `15 * * * *`, lease 5 min, stale after 3h in the ops digest). If Sentry cron monitors are allowlisted per job (`settings.sentry_cron_jobs`), add this id to the allowlist to get check-ins; otherwise the ops digest's stale-job section covers it.
- The migration was renumbered from `0168` to `0169` because a sibling branch (issue #671) already owns the `0168` prefix. Nothing was applied to prod under the old number, so there is nothing to undo; just be sure `0168` from that branch lands too.
- No env vars. `enrollments` gains `pending_cancellation_at` / `pending_cancellation_requested_at` (0132's validator has no `additionalProperties: false`, so no change needed).

## Risk / rollback
If the new job stalls, end-of-period families keep attending past month end (the stale-job dead-man switch reports it within 3h); nothing is double-billed because billing was voided at request time and the processor's second sync is idempotent. If the migration is applied but the deploy is rolled back, the old code still works: it never writes a `cancel_at_period_end` row and 0113's key is a subset of the new partial index; already-pending cancellations would then never flip — run the job forward again or cancel those enrollments by hand from the admin roster (each has a `cancellation_scheduled` timeline row and `pending_cancellation_at`). Rolling back the code alone before the migration is applied changes nothing. To revert entirely, revert the PR and cancel any pending enrollments by hand; the validator/index changes are backward compatible and can stay.
