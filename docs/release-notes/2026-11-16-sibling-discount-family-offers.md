# sibling-discount-family-offers

PR: #1191

## What changed
Settings > Billing rules has a new Family offers card (owner only to save, audited). It ships switched off. The owner can turn on an automatic sibling discount and set its percentage (no default; 0.01% to 100%), which child pays full price (highest tuition, lowest tuition or first enrolled) and whether it covers every class of each other child or one class each. The monthly run and admin "Bill this month" then price each other child's monthly tuition with it, on the existing "Sibling discount" line; a larger manual tuition discount on the same class wins (ties go to the manual one) and the two never add up. The family is the set of enrollments the run actually bills that month (deferred, skipped and pending-cancellation months do not count), found under any of the parent's linked ids. Each enrollment-month is decided once, when it is first priced, and recorded, so retries and orphan recovery charge the same amount and a month already billed under any invoice is never repriced. A month is decided against what is already decided: if a sibling already paid full price that month, or was recorded as the full-price child and is still billed that month, the others are discounted; otherwise the owner's rule picks the full-price child among the children not yet decided. A month therefore keeps exactly one full-price child whatever the run order or a mid-run setting change, except when a full-price child that was priced but never invoiced leaves the family after a sibling was decided against it. A setting or decision with an out-of-range percentage (only a hand edit can store one) applies no sibling discount and pages Sentry instead of stopping the run. A mid-month class move prices both sides with the discount that month's invoice carries. The card also stores the referral programme's values (credits, hold days, yearly cap, expiry, trigger) with its switch disabled and marked Coming soon; the API refuses to switch it on until the referral logic is built. New API: `GET`/`PUT /api/v2/admin/billing/family-offers` (PUT owner only).

## Deploy notes
Migration `0237_sibling_discount_decisions` creates the unique index `sibling_decision_enrollment_period_unique` on the new `sibling_discount_decisions` collection (academy, enrollment, period) and the index `parent_user_children` on `students` (academy_id, parent_user_id), so the sibling lookup by either parent field is an index seek. It applies through the release_command; nothing to watch beyond it creating the two indexes. No env vars.

Read-only pre-deploy check (do not add an index from it): confirm no enrollment has two active manual discounts, since the resolver weighs the sibling discount against the one active manual policy. Expect no rows:

```
db.enrollment_discounts.aggregate([
  { $match: { status: "active" } },
  { $group: { _id: { academy_id: "$academy_id", enrollment_id: "$enrollment_id" }, n: { $sum: 1 }, ids: { $push: "$discount_id" } } },
  { $match: { n: { $gt: 1 } } }
])
```

## Risk / rollback
Nothing changes for any academy until the owner switches the sibling discount on, and with it off the monthly run writes no decision rows. If prices look wrong, switching it off stops new decisions at once; months already decided keep their decision (by design, so a retry never changes a charge), so delete the affected `sibling_discount_decisions` rows only for months not yet invoiced if they must be re-priced. Roll back the code by reverting the merge commit; the collection and index can stay or be dropped. Known limits: siblings are found through the students' parent fields, so a child linked to the parent only through `enrollment.parent_id` or `parent_user_id` is not counted. A new enrollment's prorated first month, charged at checkout, gets no sibling discount (the same as manual discounts today); the sibling discount starts with the next monthly invoice. A month already billed keeps its price: if the full-price child's invoice is voided or refunded after a sibling was billed discounted, the sibling's month is not repriced. A family whose children were billed before the switch-on keeps those full-price months, and the children billed afterwards are discounted. A relative billed through checkout proration, or before switch-on, takes the full-price slot for that month. If the full-price child has a larger manual discount, nobody in the family pays list price that month. If a full-price child that was priced but never invoiced (a voided "Bill this month" draft) leaves the family after a sibling was decided against it, that month has no full-price child.
